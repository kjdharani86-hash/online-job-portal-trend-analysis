Software Process & Agile Development

Agile Scrum / Iterative Lifecycle
1.1 Software Development Lifecycle (SDLC) Model Comparison

For the Online Job Portal and Employment Trend Analysis System, an Agile-Scrum Iterative Development Model was selected over the traditional linear Waterfall model to support continuous integration, early stakeholder feedback, and iterative verification across multi-course deliverables.

Lifecycle Model Characteristics Advantages for Project Evaluation for Scenario 22
Classical Waterfall Model Linear, sequential phases (Requirements → Design → Coding → Testing). Clear milestones and structured formal sign-offs. Rejected: Inflexible to changes; testing delayed until late stages.
Spiral / Risk-Driven Model Cyclic progression addressing risk assessment at every loop. Strong risk management for high-risk software. Overkill: High management overhead for academic scenario.
Agile Scrum (Selected) Iterative sprints (2-week increments), cross-functional, continuous testing. Fast delivery of increments (Database → Service → Web GUI → ML Charts). Adopted: Perfectly matched the 4 integrated curriculum courses.

UNIT 4

Software Testing Strategies, Techniques & Test Cases

Black-Box, White-Box & 16-Case Matrix
4.1 Testing Levels & Strategies

Testing was performed hierarchically across all four software engineering levels: Unit Testing (DAOs, regular expression validators, model getters/setters), Integration Testing (Service layer coordinating with SQLite JDBC transactions), System Testing (End-to-end recruitment drives and reporting), and Acceptance Testing (Verification against Scenario 22 deliverables).

Black-Box Testing (Functional)
  • Equivalence Partitioning (EP):
    • CGPA valid partition: [0.00, 10.00]. Invalid partitions: < 0.00, > 10.00.
    • Phone number partition: 10 numeric digits. Invalid: alphabetic or length ≠ 10.
  • Boundary Value Analysis (BVA):
    • CGPA tested at boundaries: -0.01 (Reject), 0.00 (Accept), 6.00 (Cutoff boundary), 10.00 (Accept), 10.01 (Reject).
White-Box Testing (Structural)

Basis Path Testing & Cyclomatic Complexity for isEligible():

Formula: V(G) = P + 1 (where P = number of predicate decisions)
Predicates: (1) CGPA ≥ Cutoff, (2) Dept == 'ALL', (3) Dept in AllowedList
V(G) = 3 + 1 = 4 Independent Execution Paths
  1. Path 1: CGPA < Cutoff → Throws IneligibleCandidateException.
  2. Path 2: CGPA ≥ Cutoff & Dept == 'ALL' → Returns true.
  3. Path 3: CGPA ≥ Cutoff & Dept ∈ List → Returns true.
  4. Path 4: CGPA ≥ Cutoff & Dept ∉ List → Throws IneligibleCandidateException.

5.1 Software Cost & Effort Estimation (Basic COCOMO Model)

The Constructive Cost Model (COCOMO) was applied to estimate software development effort, schedule duration, and recommended staffing. The project falls under the Organic Mode (small, well-understood domain with small team).

COCOMO Mathematical Equations (Organic)
Effort: E = ab × (KLOC)bb [person-months]
Development Time: D = cb × (E)db [months]
Staff Size: SS = E / D [persons]
Constants for Organic Mode:
ab = 2.4, bb = 1.05, cb = 2.5, db = 0.38
Codebase Metric Inputs
  • Java Backend (Model, DAO, Service, Main): 1,120 LOC
  • Python Analytics & Web Dashboard: 510 LOC
  • SQL Schema, Seed Data & Queries: 190 LOC
  • Total Delivered Source Code (KLOC): 1.82 KLOC
Calculated Project Estimates
Estimated Effort (E): 2.4 × (1.82)1.05 = 4.50 Person-Months
Development Duration (D): 2.5 × (4.50)0.38 = 4.43 Months
Average Staff Required (SS): 4.50 / 4.43 = 1.02 ≈ 1 Engineer
Project Productivity: 1,820 LOC / 4.50 PM = 404 LOC/PM
Matches the single-student project allocation schedule spanning academic semester milestones.
5.2 Risk Management (RMMM Plan)

The Risk Mitigation, Monitoring, and Management (RMMM) plan identifies potential project risks, estimates risk exposure, and establishes formal mitigation procedures.

Risk Category Identified Risk Description Prob (P) Impact (I) Mitigation Strategy Management & Monitoring
Data Integrity Duplicate applications submitted for same vacancy. High (0.8) High Dual-layer protection: DB compound UNIQUE constraint + Service layer pre-check. Caught via DuplicateApplicationException; flash alert shown to user.
Compliance Students applying without meeting CGPA cutoffs. High (0.7) Medium Pre-submission validation in service layer comparing student CGPA against vacancy cutoff. Throws IneligibleCandidateException with explicit reasoning.
Security SQL Injection via interactive user inputs. Medium (0.4) Critical 100% Parameterized queries with PreparedStatement and SQLite parameters. Static code audit and input regex validation.
